## 二、核心设计原则

| 设计原则 | 具体要求 | 实现策略 |
| --- | --- | --- |
| **高并发** | ≥100万同时在线 | 三级架构 + 水平扩展 + 异步队列 |
| **高可用** | 99.99% SLA | 多活部署 + 自动故障转移 |
| **低延迟** | 首Token ≤ 2s | 边缘缓存 + 推理优化 + 就近接入 |
| **数据安全** | 工业数据不出厂 | 分级存储 + 国密加密 + 零信任网络 |
| **弹性伸缩** | 峰值5倍冗余 | K8s HPA + GPU弹性池 |
| **知识隔离** | 各分公司数据隔离 | 多租户 + 命名空间隔离 |

**推理优化策略：**

```python
# 智能路由伪代码
class InferenceRouter:
    def route(self, query, user_context):
        # 1. 热点知识缓存命中 → 直接返回（命中率目标>40%）
        cached = self.semantic_cache.search(query, threshold=0.95)
        if cached:
            return cached  # < 50ms

        # 2. 简单FAQ类问题 → 7B轻量模型
        complexity = self.complexity_classifier(query)
        if complexity == "simple":
            return self.light_model_cluster.infer(query)  # ~200ms

        # 3. 复杂推理/分析 → 72B主力模型
        elif complexity == "complex":
            return self.main_model_cluster.infer(query)  # ~2-5s

        # 4. 长文档分析 → 长上下文专用模型
        elif complexity == "long_context":
            return self.long_ctx_cluster.infer(query)  # ~5-10s
```

## 六、知识库构建与治理（续）：从“能用”走向“可控、可演进”

下面在你已有的总体架构基础上，把**工程实施**里最容易踩坑、但又决定可规模化落地的部分补齐：数据接入、知识治理、索引构建、同步分发、训练/评测闭环。并在关键链路引入 **Pulsar MQ**（在某些场景比Kafka更适合）。

## 6.1 数据接入与采集：集团级“数据入口”标准化

### 6.1.1 数据源分类与接入方式（建议统一成“连接器”体系）

1. **文档类**：SOP、设备手册、工艺规程、质量文件、EHS、制度、培训材料
- 来源：SharePoint/企业网盘/本地NAS/邮件归档/ERP附件
- 接入：定时扫描 + Webhook（变更触发）
1. **结构化系统类**：ERP/MES/PLM/QMS/LIMS/SCADA/CMMS
- 接入：CDC（Change Data Capture）或API增量拉取
- 落地：ODS（Operational Data Store）+ 元数据目录
1. **实时事件类**：传感器告警、产线事件、质检结果流、设备状态、能耗
- 接入：IoT网关→消息总线→流处理→“事件知识”沉淀
1. **经验与对话类**：专家答疑、工单处理、巡检记录、维修记录
- 接入：从工单系统/IM/热线系统同步，形成“问答对+证据链”

---

## 6.2 为什么在这里引入 Pulsar MQ（而不是处处Kafka）

集团场景常见痛点：**跨地域、跨系统、数据隔离、多租户、回溯重放、长周期积压**。Pulsar在以下环节优势明显：

### Pulsar适用的关键场景

- **多租户隔离**：Pulsar原生 tenant/namespace/quota，非常适合“总部+分公司”隔离治理。
- **Topic数量巨大**：几十工厂 × 多业务流 × 多数据源，Topic可能成千上万，Pulsar扩展性更友好。
- **冷热分层存储**：Pulsar + BookKeeper + Tiered Storage（S3/MinIO）可以把历史消息下沉，适合审计、回溯、模型训练数据回放。
- **跨地域复制**：Pulsar Geo-replication 可做“中心-区域-工厂”分级同步。
- **流批一体**：同一条消息既能实时处理，也能长期沉淀用于离线构建、评测、训练。

> 建议策略：
> 
> - **Kafka**：适合“单区域内高吞吐、成熟生态”场景（比如日志采集、传统ETL）。
> - **Pulsar**：适合“多租户 + 多地域 + 长周期可回溯 + Topic爆炸”场景（集团知识库非常典型）。

## 七、引入Pulsar后的“知识流水线”实施架构（可执行）

### 7.1 统一的知识生产流水线：事件驱动（Event-Driven Knowledge Pipeline）

**核心思想**：所有“文档变更、系统变更、事件流、人工审核结果”都变成事件，进入Pulsar，再由不同消费者完成解析、入库、索引构建、分发。

### 7.1.1 Topic 与命名空间设计（多租户）

- Tenant：`group`（集团总租户） + `subsidiary-xx`（分公司租户）
- Namespace：
    - `group/knowledge-ingest`
    - `group/knowledge-index`
    - `subsidiary-xx/knowledge-local`
- Topic命名示例：
    - `persistent://group/knowledge-ingest/doc-change`
    - `persistent://group/knowledge-ingest/db-cdc`
    - `persistent://group/knowledge-ingest/iot-event`
    - `persistent://group/knowledge-index/embedding-task`
    - `persistent://group/knowledge-index/reindex-task`
    - `persistent://group/knowledge-index/vector-upsert`
    - `persistent://group/knowledge-index/es-upsert`
    - `persistent://group/knowledge-index/kg-upsert`
    - `persistent://group/audit/llm-trace`

### 7.1.2 关键服务与订阅模式

- `DocWatcher`（生产者）：文档变更→发`doc-change`
- `DocParser`（消费者，Shared订阅）：解析、OCR、结构化→发`chunk-ready`
- `Embedder`（消费者，Key_Shared订阅）：按docId/工厂路由，避免同一文档乱序→发`vector-upsert`
- `IndexWriter-ES/Milvus/Neo4j`：各自消费对应upsert topic，幂等写入
- `SyncDistributor`：把总部知识增量分发到区域/工厂边缘（Geo-replication 或应用层转发）
- `QualityGate`：抽检、评测、置信度；不通过则发`quarantine`

## 八、总部-区域-工厂的知识同步与隔离策略（最关键）

### 8.1 知识分级：必须做“知识域（Knowledge Domain）”

建议至少分三层：

1. **集团公共知识（Global）**
- 制度、通用安全规范、通用设备维护原则、通用培训
- 同步：总部→所有区域→所有工厂（只读）
1. **区域/事业部知识（Regional/BU）**
- 某区域工艺差异、供应商差异、区域合规
- 同步：区域→辖区工厂（只读或有限编辑）
1. **工厂本地知识（Local）**
- 具体产线SOP、设备参数、现场临时改动、班组经验
- 原则：默认不出厂；必要时做脱敏与汇总上行（可选）

### 8.2 同步机制两种路线（可组合）

**路线A：Pulsar Geo-replication（推荐）**

- 优点：消息级增量，天然可回放、可审计
- 用法：总部集群与区域集群之间做namespace级复制；工厂边缘也可做轻量代理（Pulsar Proxy）

**路线B：应用层增量同步（补充）**

- 通过“知识变更事件+签名+水位”方式同步向量/索引/原文
- 优点：对边缘资源要求低；可按策略过滤（只下发必要子集）

> 实操建议：
> 
> - 总部↔区域：Geo-replication
> - 区域↔工厂：应用层增量（因为工厂网络不稳定、资源差异大）

## 九、索引构建的工程细节（避免“建库后不可用”）

### 9.1 三索引并存：向量 / 全文 / 图谱

- 向量索引：语义召回（Milvus）
- 全文索引：精确匹配、编号、条款（ES）
- 图谱索引：设备-工序-故障-备件-专家的关系推理（Neo4j）

### 9.2 Parent-Child Chunk + 引用溯源（必须落地）

每个chunk必须带元数据：

- `doc_id, doc_version, factory_id, domain, confidentiality_level`
- `section_path`（章节路径）
- `parent_chunk_id`（父块用于上下文扩展）
- `source_uri`（来源URL/文件路径）
- `hash`（幂等与去重）
- `effective_date/expiry_date`（生效/过期）

> 没有这些字段，后期“权限隔离、版本回滚、审计追责、索引重建”都会变成灾难。
>

## 十、对话与RAG线上链路增强：缓存、降级、护栏

### 10.1 语义缓存（Semantic Cache）与Pulsar的结合

- 对于高频问题：缓存答案 + 引用片段 + 置信度
- 缓存命中后直接返回，同时把命中事件发到 Pulsar：
    - `group/observability/cache-hit`
    - 用于热点知识挖掘、知识补全、FAQ固化

### 10.2 降级策略（确保百万用户下系统不崩）

分级降级（按资源与负载）：

1. 命中缓存 → 直接返回
2. 轻量模型 + Top3检索片段
3. 仅返回检索结果（不调用大模型），给出“证据列表”
4. 返回“工单/专家通道”引导

降级事件同样写入 Pulsar（用于事后容量评估）：

- `group/observability/degrade-event`

## 十一、评测与持续改进闭环（生产系统必须有）

### 11.1 线上可观测性：Trace 到 token 级

每次RAG请求记录（脱敏后）：

- 检索命中率、召回文档、rerank分数
- 生成耗时、首token延迟、token数
- 置信度、是否触发敏感拦截
- 用户反馈（👍👎、纠错）

这些记录建议进 Pulsar：

- `group/audit/llm-trace`（长存）
- 下游落地 ClickHouse/ES 用于分析

### 11.2 离线评测集构建与回放

- 从 `llm-trace` 回放构建评测集（覆盖不同工厂、不同知识域）
- 通过Pulsar的消息回放能力，重放历史高价值问题，对比不同模型/不同chunk策略效果
